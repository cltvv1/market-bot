# Открытые вопросы

## Storage and backup

- Production retention period and local copy count.
- Destination and encryption for the second external copy.
- Retention policy for remote messenger media.
- Final upload limits after measuring real traffic.
- Whether antivirus scanning is mandatory before production document uploads.

В документ включены только решения, которых нет в исходном коде и предоставленном бизнес-контексте. Они не блокируют сам аудит, но часть из них нужна до соответствующего этапа реализации.

## 1. Перед этапом 0

### OQ-01. Какая база считается источником для baseline?

Нужно определить:

- есть ли одно фактическое рабочее окружение или несколько расходящихся копий;
- содержит ли текущая локальная backup-копия всю актуальную историю;
- можно ли использовать обезличенную копию для migration tests.

Почему важно: `synchronize: true` мог создать schema drift, которого нет в entities.

### OQ-02. Какие объёмы и сроки хранения файлов обязательны?

Нужны правила отдельно для:

- фото оборудования;
- видео/голосовых сообщений;
- счетов;
- регистрационных PDF;
- подписанных согласий;
- инженерных документов.

Почему важно: определяет лимиты upload, storage, backup, retention и необходимость антивирусной обработки.

### OQ-03. Где будет размещён первый публичный пилот?

Нужно знать:

- ОС/сервер или облако;
- reverse proxy и TLS;
- домены сайта и админки;
- доступный persistent volume;
- допускается ли S3-совместимое хранилище;
- способ хранения secrets.

Почему важно: CORS, cookie, file provider, backup и deployment нельзя безопасно завершить только по локальной конфигурации.

### OQ-04. Какие operational recovery objectives приемлемы?

Нужно согласовать максимально допустимые:

- потерю последних данных при аварии;
- продолжительность восстановления;
- срок хранения backup;
- место хранения второй копии.

Почему важно: текущий backup покрывает только PostgreSQL и не имеет проверяемого restore schedule.

### OQ-05. Может ли один сотрудник совмещать несколько ролей? — закрыт

Решение утверждено и реализовано: один сотрудник может иметь несколько ролей, например `operator + sales_manager`. Назначения хранятся в `admin_user_roles`; permissions объединяются.

## 2. Перед этапом 1. Магазин

### OQ-06. Как показывать цену и НДС?

Нужно определить:

- цена включает НДС или нет;
- ставка/пометка для разных товаров;
- разрешён ли текст «цена по запросу»;
- кто имеет право менять цену;
- нужна ли история будущей цены.

Почему важно: цена сохраняется snapshot в заказе и отображается B2B-клиенту.

### OQ-07. Что означает отображаемое наличие?

Варианты, требующие выбора:

- «в наличии / мало / под заказ / нет» вручную;
- приблизительное количество;
- дата ожидаемого поступления;
- только текст менеджера.

Почему важно: проект не должен имитировать склад 1С, но клиенту нужен понятный статус.

### OQ-08. Какие способы и география доставки нужны в первом релизе?

Нужно подтвердить:

- самовывоз и точный адрес;
- доставка по Красноярску;
- транспортная компания;
- кто рассчитывает стоимость;
- можно ли оформить заказ без точного адреса.

Почему важно: `DeliveryMethod` входит в первый заказ.

### OQ-09. Как анонимный web-клиент получает счёт до личного кабинета?

Нужно выбрать рабочий канал первого релиза:

- защищённая страница заказа по token;
- подтверждённый Telegram/MAX;
- подтверждённый email;
- комбинация.

Предлагаемое безопасное значение по умолчанию: защищённая страница + messenger при подтверждённой привязке.

### OQ-10. Какой формат выгрузки каталога реально доступен из 1С?

Нужны образцы CSV/XLSX и правила:

- стабильный SKU/артикул;
- категории;
- цены;
- остаток/наличие;
- изображения;
- архивные товары.

Почему важно: первый магазин можно заполнить вручную, но модель mapping лучше не переделывать после массового импорта.

### OQ-11. Кто является владельцем каталога?

Нужно подтвердить, редактирует ли каталог:

- любой менеджер по продажам;
- назначенный catalog manager;
- только superadmin.

Почему важно: влияет на permission matrix, а не требует новой роли при наличии отдельного permission.

### OQ-12. Какие реальные реквизиты и контакты сайта утверждены?

`client-ui/src/data/company.ts` содержит frontend-конфигурацию, но из кода нельзя подтвердить, какие значения production-актуальны и юридически одобрены.

## 3. Перед этапом 2. Сервисные заявки

### OQ-13. Как выглядит утверждённая матрица переходов сервиса?

Нужно согласовать:

- кто может переводить заявку в каждый внутренний статус;
- какие статусы требуют комментарий;
- можно ли завершить неоплаченную заявку;
- может ли инженер завершить или только передать оператору;
- когда заявка считается закрытой, а не выполненной.

Почему важно: текущий backend разрешает действия почти независимо от предыдущего статуса.

### OQ-14. Какие поля обязательны для первой универсальной web-заявки?

UI уже содержит широкий набор, но нужно отделить:

- обязательные для любой услуги;
- обязательные только для выезда;
- обязательные только для организации;
- необязательные до уточнения оператором.

Почему важно: schema должна быть бизнес-правилом backend, а не только frontend validation.

### OQ-15. Какой ответ доступен анонимному web-клиенту?

Нужно решить, достаточно ли:

- status/history/comments на защищённой странице;
- полноценного web-чата;
- предложения привязать Telegram/MAX.

Предлагаемый первый шаг: status + сообщения оператора на защищённой странице, без real-time websocket.

### OQ-16. Как учитывать материалы инженера на первом этапе?

Варианты:

- свободный текст;
- строки «наименование/количество» без справочника;
- выбор из выгрузки номенклатуры 1С.

Предлагаемый первый шаг: структурированные строки без попытки вести склад.

### OQ-17. Нужны ли SLA/дедлайны заявок уже в первом pilot workflow?

Оператор должен следить за просроченными заявками, но правила просрочки не определены:

- от какого события считать;
- зависит ли срок от приоритета;
- рабочие часы и выходные;
- кому эскалировать.

Это можно отложить после базового assignment/status, если нет утверждённых правил.

## 4. Перед этапом 4. Клиенты и организации

### OQ-18. Как подтверждается право представителя организации?

Нужно выбрать допустимые способы:

- приглашение существующим владельцем;
- ручное подтверждение оператором;
- документ;
- код на корпоративный канал;
- другой бизнес-процесс.

Почему важно: текущая привязка по одному ИНН сразу создаёт active owner и небезопасна для кабинета.

### OQ-19. Как оператор разрешает спорное объединение клиентов?

Нужно определить:

- какие доказательства он видит;
- кто имеет право подтвердить merge;
- нужен ли принцип двух подтверждений для организаций;
- допустимо ли разъединение ошибочного merge.

### OQ-20. Какие провайдеры email и SMS допустимы?

SMS не блокирует первые этапы, но перед реализацией OTP нужны:

- provider;
- юридический договор;
- sender name;
- стоимость/лимиты;
- требования к хранению delivery logs.

## 5. Перед этапами 5-7

### OQ-21. Как идентифицировать оборудование без серийного номера?

Для части весов, принтеров, компьютеров или старого оборудования серийный номер может быть неизвестен. Нужны правила:

- внутренний inventory number;
- manufacturer/model/location combination;
- временная unidentified запись;
- последующее merge.

### OQ-22. Какие данные АТОЛ и ОФД компания юридически и технически может получать?

Нужно подтвердить:

- наличие документированного API;
- scope партнёрского доступа;
- sandbox;
- rate limits;
- право хранить полученные данные;
- перечень организаций, давших согласие.

До ответа интеграции остаются только архитектурными портами.

### OQ-23. Какие интервалы напоминаний по ФН и ОФД утверждены?

Нужны:

- набор предупреждений до даты;
- повтор после недоставки;
- рабочее время отправки;
- момент создания задачи оператору;
- правила для уже просроченных записей.

### OQ-24. Какие сообщения считаются обязательными сервисными, а какие маркетинговыми?

Нужна юридически согласованная классификация и тексты согласий/отказа. Код не может самостоятельно определить правовой режим.

## 6. Перед этапом 8. Подборщик

### OQ-25. Кто утверждает правила рекомендаций?

Нужно определить владельца:

- директор;
- ведущий инженер;
- менеджер по продажам;
- совместное утверждение.

Также нужны первые утверждённые вопросы, ответы и product attributes, на которых строится рекомендация.
