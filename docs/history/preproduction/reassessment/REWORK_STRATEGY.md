# Стратегия переработки client-ui

## Исходное решение

React/router/session/API foundation работает. Визуальный слой накопил конфликтующие CSS overrides, а продуктовый слой смешивает рабочий сервис с демонстрационным магазином. Поэтому решение должно одновременно:

- не переписать рабочую web-session и формы;
- перестать выдавать localStorage checkout за реальный заказ;
- сформировать отличимый B2B-образ ЦТО и поставщика;
- дать место будущему Product/Order backend без второй полной переделки.

## Вариант A — точечная визуальная переработка

**Сохраняется:** все pages, текущий Layout, component markup, CSS selectors и frontend data.

**Заменяется:** tokens, typography, spacing, некоторые cards/header/hero, реальные images.

**Ценность:** быстро уменьшает визуальный шум и возвращает фирменный зелёный.

**Сложность:** M. **Риск поломки:** medium из-за 4369-line cascade. **Сопровождение:** остаётся дорогим. **Магазин:** почти не приближает server-backed order. **Параллельная версия:** не нужна.

Главный недостаток: сохраняет ложную продуктовую композицию и CSS-слои, из-за которых следующий экран снова придётся «переопределять».

## Вариант B — новая оболочка, сохранение data layer

**Сохраняется:** React/Vite, router/routes после product review, WebSessionBoundary, credentialed API model, types, registration/service logic, Cart state как временный prototype, часть UI primitives после accessibility fixes.

**Заменяется:** site shell, design tokens, CSS structure, page templates, navigation, hero, product cards/gallery, form layout, overlay primitives, responsive rules. API client делится на domain modules; mock и real paths становятся явно разными.

**Ценность:** решает визуальную цельность и позволяет честно разделить working service и future shop, не повторяя backend/session работу.

**Сложность:** L. **Риск поломки:** medium-low при vertical regression tests. **Сопровождение:** существенно лучше. **Магазин:** создаёт готовую UI-рамку, но Product/Order backend остаётся отдельным этапом. **Параллельная версия:** отдельное приложение не нужно; страницы переносятся по одной внутри текущего router.

## Вариант C — controlled rewrite

**Сохраняется:** только API contracts и отдельные types/algorithms.

**Заменяется:** весь `client-ui` новой структурой, component system и routes.

**Ценность:** максимально чистая CSS/component база.

**Сложность:** XL. **Риск поломки:** high для registration/service/session. **Сопровождение:** потенциально хорошее после завершения, но две версии придётся держать до parity. **Магазин:** задерживается из-за повторной реализации уже рабочих сценариев.

Полный rewrite оправдан только при смене frontend stack или подтверждённой невозможности отделить бизнес-логику. Ни того, ни другого код не показывает.

## Рекомендация

Выбрать **B**.

Последовательность будущих решений:

1. Выбрать коммерческую модель первой версии: каталог-заявка или настоящий order workflow.
2. Утвердить реальные контакты, legal copy, service catalog, product categories и доступные media assets.
3. Выбрать одно из дизайн-направлений ниже и собрать page inventory: оставить, объединить, отложить.
4. Зафиксировать design tokens, shell, navigation и accessible primitives.
5. Перенести сначала Home + Service + Contacts, затем Catalog/Product, затем рабочие forms.
6. Подключить реальный Product/Order backend только после решения о ценах/наличии/доставке; до этого checkout скрыть или назвать отправкой списка менеджеру.
7. После parity удалить заменённые selectors/legacy client styles, а не оставлять второй слой overrides.

## Черновой дизайн-бриф

### Факты из проекта

- Компания продаёт кассовое и торговое оборудование и оказывает физический/удалённый сервис.
- Основная аудитория B2B; типовые задачи связаны с ККТ, 54-ФЗ, ФН, ОФД, маркировкой и автоматизацией.
- Сервисные обращения и регистрация уже являются рабочими digital flows; магазин пока demo.
- Логотип монохромный; в ранних tokens присутствовал рабочий зелёный.

### Желаемое впечатление

Надёжный местный технический партнёр: знает модели и регламент, быстро принимает обращение, не скрывает, что требует звонка/проверки, умеет сопровождать оборудование после продажи.

### Характер

- спокойный, конкретный, технически компетентный;
- не безликий marketplace и не SaaS dashboard;
- достаточно плотный для сравнения оборудования;
- дружелюбный без рекламной гиперболы.

### Визуальные правила

- **Цвет:** светлая нейтральная основа, графитовая структура, фирменный зелёный для primary/active/service, отдельные amber/red semantic states. Не делать весь сайт зелёным или бежевым.
- **Типографика:** функциональный grotesk с хорошей кириллицей; умеренные display sizes, табличные цифры для цен/серийных номеров, ясная шкала 12/14/16/20/28/40–52.
- **Изображения:** реальные товары на нейтральном фоне, детали портов/шильдиков, реальные рабочие места и сотрудники сервиса. Не использовать абстрактные 3D-устройства вместо inspectable product.
- **Иконки:** line icons только для navigation/status/support; не заменять ими товар или целую маркетинговую секцию.
- **Карточки:** product cards плотные, с фото, моделью, 3–4 сравнимыми параметрами, проверяемой ценой/availability и одним primary action. Service направления лучше делать списком/матрицей, а не одинаковой card wall.
- **Формы:** одно основное действие, прогресс без декоративного sidebar, sticky mobile footer только если не закрывает поля, первая ошибка получает focus.
- **Анимации:** 120–200 ms для menu/filter/status; без parallax, floating blobs и бесконечных декоративных loops.
- **Mobile:** 360 px first-class, быстрый phone/service action, компактный header, filter drawer, устойчивые 44 px touch targets, следующий контент виден под hero.

### Структура главной

1. Короткий first viewport: literal offer + «Подобрать оборудование» и «Нужна помощь с кассой».
2. Два явных пути: купить/оснастить и починить/обслужить.
3. Основные product categories с реальными объектами.
4. Service entry с типовыми проблемами и сроком ответа только после утверждения SLA.
5. Конкретные доказательства: авторизации/бренды/город/мастерская/процесс, без случайных метрик.
6. Контакты и рабочий график.

### Запрещённые приёмы

- success заказа без server persistence;
- псевдо-наличие и скидки;
- giant hero на весь mobile viewport;
- одинаковые rounded cards для любой информации;
- случайные цифры/метрики и непроверенные SLA;
- monochrome filter, скрывающий вид продукта;
- декоративные gradients/orbs, SaaS-style dashboard imagery;
- второй слой CSS overrides поверх старого visual system.

## Дизайн-направления

### 1. Технический центр и поставщик — рекомендуется

**Первое впечатление:** уверенный сервисный центр с хорошим каталогом. **Типографика:** нейтральный индустриальный grotesk. **Цвет:** white/graphite + clear VITMA green + semantic amber/red. **Сетка:** 12-column desktop, плотный catalog, широкие unframed sections. **Карточки:** минимум decoration, технические характеристики выровнены для сравнения. **Изображения:** реальные product shots и сервисный процесс.

Home строится вокруг двух путей «оборудование» и «сервис». Catalog напоминает профессиональную товарную ведомость, Service form — спокойный рабочий wizard. Mobile сокращает marketing и выносит быстрый звонок/заявку.

Плюсы: лучше всего отражает B2B и существующий backend. Минусы: требует качественных реальных фото и дисциплины content. Риск шаблонности: low.

### 2. Инженерный каталог

**Первое впечатление:** точность, спецификации, совместимость. **Типографика:** compact grotesk + mono только для SKU/serial. **Цвет:** холодные neutral, зелёный для verified/available, синий для information. **Сетка:** плотная, больше таблиц и comparison rows. **Карточки:** почти без теней, характеристики важнее marketing. **Изображения:** front/side/ports/package.

Home быстрее ведёт в категории и selector; Catalog является главным продуктом; service доступен как persistent utility. Mobile использует list cards вместо крупных плиток.

Плюсы: высокая полезность для знающего покупателя. Минусы: может быть сухим для малого бизнеса, требуется чистая product data model. Риск шаблонности: low, риск «дистрибьюторского прайса»: medium.

### 3. Региональный сервис-партнёр

**Первое впечатление:** живые специалисты рядом и полное сопровождение точки. **Типографика:** humanist sans с хорошей кириллицей. **Цвет:** больше белого, зелёный и тёплый supporting accent, но без beige dominance. **Сетка:** editorial service stories + compact shop modules. **Карточки:** кейсы/процессы вместо набора преимуществ. **Изображения:** команда, мастерская, установки у клиентов, реальные товары.

Home делает сервис первым, магазин вторым. Catalog остаётся функциональным, Service form более conversational. Mobile подчёркивает телефон, график и статус обращения.

Плюсы: сильная локальная дифференциация и доверие. Минусы: требует настоящих фото/кейсов и может недооценить e-commerce цель. Риск шаблонности: medium без уникальных материалов.

## Риски следующего этапа

- Начать UI до решения «каталог-заявка или заказ» и снова нарисовать ложную функцию.
- Сохранить оба visual systems и наращивать specificity.
- Попытаться одновременно redesign, Product/Order backend, account и bot decomposition.
- Использовать demo contacts/products как content baseline.
- Добавить shop tabs в монолитный admin App без feature decomposition.
