# CO-3C Order fulfillment and completion workflow

## 1. Baseline

CO-3C starts from `c1c424fb3b632507bddf9ac2487e33e86b9cb781`, the
merge commit of CO-3B. The baseline already contains order intake, immutable
commercial quotes, invoice revisions, payment proofs, and manual confirmation
of full payment.

## 2. CO-3C scope

This package adds two explicit backend commands: `paid -> fulfilled` and
`fulfilled -> completed`. It also extends assignment through the longer sales
workflow. It does not add a generic status endpoint or any external side
effect.

## 3. Paid vs fulfilled vs completed

`paid` means that the assigned manager confirmed full receipt of money.
`fulfilled` means that all goods and applicable services were delivered in the
real world. `completed` means that realization data and final-document delivery
were recorded and ordinary manager work is closed. These facts are separate
and ordered.

## 4. Whole-order-only fulfillment

The fulfillment command confirms the entire order. CO-3C has no quantities,
partial shipments, backorders, warehouse allocation, serial-number assignment,
returns, or split fulfillment.

## 5. Fulfillment methods

The fixed methods are `pickup`, `courier`, `transport_company`, `service_only`,
and `mixed`. Arbitrary values are rejected by DTO validation, domain
normalization, and database constraints.

## 6. Fulfillment field model

An Order stores actual fulfillment time, accountable staff ID, method,
optional recipient, carrier and tracking details, and an internal comment. No
passport, power-of-attorney number, signature, geolocation, or bank data is
stored.

`transport_company` requires a carrier. `service_only` forbids carrier and
tracking fields and requires a comment. `mixed` requires a comment. A physical
method differing from the immutable planned `deliveryType` also requires an
explanation; the original delivery snapshot is never rewritten.

## 7. Fulfillment timestamp

`fulfilledAt` defaults to command time. An explicit value uses the shared
strict absolute timestamp contract: full calendar date, uppercase `T`, seconds,
optional one-to-nine fractional digits, and uppercase `Z` or a numeric offset.
The maximum future tolerance is five minutes. Fulfillment cannot precede
`paymentReceivedAt`.

## 8. Fulfill prerequisites

The locked Order must be `paid`, have the expected version, be assigned to the
actor, contain a complete payment-confirmation bundle, retain a fully priced
confirmed Quote and a current invoice domain row, and contain no fulfillment or
completion facts. Physical invoice availability and payment proof are not
prerequisites.

## 9. Fulfill command transaction

`POST /admin/api/orders/:id/fulfill` requires `orders.fulfill`. In one
PostgreSQL transaction it locks the Order, rechecks all invariants, writes the
fulfillment bundle, increments `Order.version` once, adds a customer-visible
`fulfilled` event, and records `order.fulfilled` in Audit Log. It performs no
messenger, provider, warehouse, delivery, EDO, or 1C call.

## 10. Completion field model

An Order stores backend command time, accountable staff ID, realization number
and calendar date, final-document delivery method and kinds, delivery time, and
an internal completion comment.

## 11. Realization number and date

The manager supplies a trimmed non-empty realization number up to 100
characters. Leading zeroes, letters, hyphens, and slashes are preserved;
control characters are rejected. The value is not globally unique and is not
generated by VITMA. `realizationDate` is a strict `YYYY-MM-DD` calendar date
stored as PostgreSQL `date`, without environment-dependent `Date` parsing.

## 12. Final document delivery methods

The fixed methods are `edo`, `paper`, `mixed`, and `not_required`.
`not_required` is allowed only for an individual customer and requires a
non-empty reason.

## 13. Final document kinds

The fixed kinds are `upd`, `invoice_factura`, `torg12`, `act`, and `other`.
The array is unique, bounded to five items, validated against the fixed set,
and stored in deterministic canonical order. `other` requires a comment.

## 14. Why final binary uploads are deferred

Final documents may live in EDO or 1C, be handed over on paper, or not apply to
an individual. Completion therefore records accountable business facts rather
than requiring a `StoredFile`. A later package can extend `OrderDocument` and
reuse FS-1 without changing the completion identity or state transition.

## 15. Complete prerequisites

The locked Order must be `fulfilled`, match `expectedVersion`, remain assigned
to the actor, contain consistent payment and fulfillment bundles, retain its
confirmed Quote and current invoice row, and have no completion facts.
Realization and document-transfer input must satisfy all conditional rules.

## 16. Complete command transaction

`POST /admin/api/orders/:id/complete` requires `orders.complete`. In one
transaction it locks and validates the Order, writes completion facts, moves
the status to `completed`, increments the version once, adds the
customer-visible `completed` event, and records `order.completed`. There are no
external calls.

## 17. Assignment continuity after confirmation

The existing assignment command now supports `submitted`, `in_review`,
`confirmed`, `waiting_payment`, `paid`, and `fulfilled`. It preserves status,
Quote, documents, payment, fulfillment, and completion facts. A real change
increments the version and records the existing reassignment event and audit;
same-manager assignment remains a no-op. Assignment is rejected for
`completed` and `cancelled`.

## 18. Phase-aware manager eligibility

Every target must be active and have `orders.read.all`. Review phases require
`orders.review`; confirmed and waiting-payment phases require both
`orders.invoice` and `orders.payment`; paid requires `orders.fulfill`; fulfilled
requires `orders.complete`. Permissions come from the current role union, not a
hard-coded role name.

## 19. ExpectedVersion and row locking

Fulfill, complete, and reassignment require a bounded `expectedVersion`. Each
command locks the Order with `pessimistic_write`, compares the exact version,
and uses a conditional version update. Successful commands increment once;
stale, invalid, denied, no-op, or rolled-back commands do not increment.

## 20. Event visibility

`fulfilled` exposes method, time, and optional customer-visible carrier and
tracking data. `completed` exposes realization and document-delivery facts.
Neither event contains internal comments, recipient personal details, payment
source, staff session data, or document contents.

## 21. Audit actions

`order.fulfilled` records compact method/time and boolean carrier/tracking
flags. `order.completed` records realization and final-document facts. Both are
transactional with the business mutation and omit comments, contacts, file
metadata, credentials, cookies, and tokens.

## 22. Client projection

Before each milestone its projection is `null`. After fulfillment the client
sees method, time, and optional recipient/carrier/tracking fields. After
completion it sees time, realization number/date, delivery method, kinds, and
delivery time. Staff identities and internal comments are not exposed.

## 23. Admin projection

Admin detail includes safe staff identities and all structured fulfillment and
completion fields, including internal comments. Admin list adds only
`fulfilledAt`, `completedAt`, and `realizationNumber`. Parameterized,
wildcard-escaped search includes realization number.

## 24. Database constraints

The database constrains supported methods and kinds, all-null or complete
bundles, required carrier/comment fields, final-document cardinality and shape,
and completion dependency on fulfillment. Staff foreign keys use
`ON DELETE RESTRICT`. Application commands remain the authoritative state
machine and customer-type boundary.

## 25. Migration and existing data

`1788355200000-AddOrderFulfillmentCompletionWorkflow` is append-only after
CO-3B. It adds nullable fields, checks, indexes, and two staff foreign keys. It
does not rewrite statuses, versions, assignment, Quote, OrderDocument, payment,
or events, and creates no synthetic fulfillment or completion fact.

## 26. Production rollback posture

`migration:revert` is suitable only for a disposable test database. Once
fulfillment, completion, or realization facts exist, automatic production
revert is data-destructive. Production recovery must use a reviewed forward
repair or an explicit data-preserving operational plan.

## 27. Future 1C adapter

A future 1C UT 11.5 adapter may invoke the same completion command/domain after
creating a realization. CO-3C stores only manual realization number and date;
it has no GUID, database reference, credentials, OData, COM, exchange files,
worker, or provider call.

## 28. Future EDO and final-document attachment

A future EDO adapter may track packages and attach final binaries through an
extended `OrderDocument` model and FS-1. CO-3C has no EDO credentials, polling,
signature validation, download, or upload route.

## 29. Deferred partial fulfillment and returns

Partial quantities, multiple shipments, corrections, reopening, realization
reversal, refunds, and returns need separate domain models and are explicitly
deferred.

## 30. Explicit exclusions

CO-3C adds no frontend work, notification or `OutboundDelivery`, final file
purpose, inventory/warehouse behavior, carrier API, 1C/EDO integration,
invoice/payment change, dependency, or real provider call.

## 31. Acceptance verdict

The backend now models full payment, whole-order real-world fulfillment, and
documentary completion as three separate, auditable, concurrency-safe facts.
The package remains intentionally manual and integration-free.
